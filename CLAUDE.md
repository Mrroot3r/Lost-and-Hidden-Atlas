# Lost & Hidden Atlas: instructions for AI models

Read `GUIDE.md` before doing anything (a research session reads sections 3 to 6, the state's row in section 8 and the lines for its area in section 10; the rest only when the job touches it). **Where the tools are:** in the repository they are in `source/tools/`. `bash source/tools/setup.sh` copies them into the working folder (`/home/claude/atlas`), and every command written `tools/…` here and in the guide is run from that working folder, not from the clone. Before researching an area run `tools/nearby.py <lat> <lon>`: it lists the places and the unchecked leads the Atlas already has there. The short version (`PROMPTS.md` holds the prompt the owner pastes to start a research session; keep it in step when a procedure changes):

- **Never push to `main`, and never merge your own pull request.** Merging publishes the site. Put your change on a new branch with `tools/publish.sh`, open a pull request, say what you verified and what you could not, and stop. The owner merges. (GUIDE.md section 3.)
- The files in the repository root (`index.html`, `app.js`, `sw.js`, `data/`, `topo/`) are **build output**. Edit `source/`, rebuild and test in the workspace. A pull request carries sources only (`publish.sh` sees to it); GitHub builds the site on the pull request to test it and again after the merge to publish it (GUIDE.md section 3). Never commit built files by hand.
- When adding places, follow the research rules in GUIDE.md section 5: every fact from a source you opened, no filling gaps from memory, both versions when sources disagree, and legal access detail stated (owner, parking, trail, hours). The one thing left out is how to get past a barrier into somewhere closed.
- Look at every new pin on the aerial with `tools/pincheck.py` before proposing it (`--lidar` in woods; it shows trailhead points too). Move a pin with `tools/pix.py`, never by hand arithmetic.
- Every US state, the District of Columbia and the ten Canadian provinces already have an outline, a region, a start city and map coverage (`tools/states.py`, `tools/outlines.py`), and 40 states and 7 provinces have one worked example each in `tools/data_states.py`. To work in any of them you only add a batch of places: one `data_<area>.py` file with `BATCH`, `PLACES` and `PIN_NOTES`. Never rename a published place `id`.
- Old rail, trolley and canal lines and the leads layer exist for New York and Massachusetts only. To add them for another state follow GUIDE.md section 8, "Lines and leads for a new state" (`tools/osm_layers.py`, `tools/ohm_state.py`, then `lines.py` and `leads.py`).
- The historic-pockets layer (old town centres first; GUIDE.md section 8, "Historic pockets for a new state") covers New York, Massachusetts, Vermont, Connecticut, New Hampshire, New Jersey, Pennsylvania. It uses marker lists from HMdb.org. Its terms: not for commercial use, always credited to HMdb.org with a link, titles and positions only. Never sign in to it and never work around its 500-markers-per-list limit. `tools/wd_nrhp.py` asks a public copy of Wikidata once and keeps the answer; never loop over it. After changing a ranking number in `tools/pockets.py` run `tools/pock_panel.py`; after changing how the pockets load run `tools/app_pockets.js`.
- Two more lead layers, vanished places (`tools/vanished.py`, the 2021 federal names file) and old mines and quarries (`tools/mines.py`, USGS records), cover nine Northeast states, Missouri and Kansas. Both are public-domain lists of unchecked leads; to add a state see GUIDE.md section 8, "Vanished places and old mines for a new state".
- Run `tools/overpass_check.py` before touching the rail and canal lines: GUIDE.md section 10 has a standing note to re-download New York from Overpass once it answers.
- "Near me" (the Near tab, and the buzz when you walk close to a place or lead) is in GUIDE.md section 9, and its Android half in section 12. After changing it run `tools/near_test.js`; after changing `NearList.java` run `tools/near_check.sh`.
- A choice made once goes under the gear (Settings); a switch flipped while looking at the map goes in Map options, which stays short (GUIDE.md section 9). After changing either sheet run `tools/settings_test.js`. After changing the Trip tab or offline saving run `tools/trip_test.js`. After changing the page layout (the grid, the layer bar, where the Map options sheet opens, the Full button) run `tools/land_test.js`: a phone on its side shows the menu on the left and the map on the right, with nothing that scrolls along the bottom edge.
- The episode kit (chapters, description, route map picture from a field log) is in GUIDE.md section 9. After changing it run `tools/kit_test.js`. Its route picture must stay on a public-domain base map.
- Never commit personal information; the repository is public.
- Run the smoke test on the workspace build (`dist/web`) before opening the pull request; `publish.sh` runs `check.py` on the sources.
- If `git push` is refused, attach the repository to the session with push access, then push again (GUIDE.md section 3). Do not retry or look for another login.
- A state's trespass-law note is optional and done only when the owner asks. The access line on each place is not optional.
- The owner uses the Atlas on an Android phone in the field. Test at phone size first.
- Places you read about but could not add go in `LEADS.md`. Edit `LEADS.md` and `GUIDE.md` in the clone after `publish.sh` has made the branch, not before. A research pull request also updates GUIDE.md: the state's row in section 8 and a line in section 10.
- The owner's visit reports (what he found on the ground, and where) come in with "Copy my additions for Claude". Run `tools/visits.py` on them and make the corrections it lists (GUIDE.md section 6). After changing the report form run `tools/visit_test.js`.
- **Asked to scan, sweep or search LiDAR? Read `LIDAR.md` and follow it step by step.** One command, `tools/lidar.py`, does the work in short runs and keeps the ledger of what has been swept and judged (`source/lidar/units/`; never edit it by hand). It covers New York and Massachusetts; another state is added only when the owner asks (LIDAR.md, "Another state"). Places found that way go in the `lidar` category as unverified leads, with an ownership check for every one (GUIDE.md section 13 is the background). Never write a private landowner's name or address into the repository. After changing `tools/lidar.py` run `tools/lidar_test.py`; after changing the stone-wall finder (`tools/lidar_walls.py`) or which pieces go on the map (`tools/walls_structure.py`) run `tools/walls_test.py` and look at `tools/lidar_walls.py test`.
- If `publish.sh` stops because `main` moved while you worked, run `tools/resync.sh` as it says, rebuild, and publish again. Do not copy files across by hand.
- Asked to review a pull request? Follow GUIDE.md section 14: `tools/review.py`, open the sources, look at the pins, report as a comment, do not merge.
- The Android app is in `android-app/` (GUIDE.md section 12). It runs the same `source/src/app.js`. You cannot run it on a phone from here: after any change to the field log, data loading or the app's Java, run `tools/app_smoke.js`, and say in the pull request what only the owner can test. Never commit a signing key.
